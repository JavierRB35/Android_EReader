# ADR-009 — Una biblioteca lógica, un estado coordinado y una copia
**Estado: histórico, sustituido definitivamente el 26/11/2026.** No implementar el coordinador, los nombres por hash, OAuth propio ni la copia obligatoria descritos a continuación. Prevalecen #103, la decisión posterior del propietario y el contrato SAF vigente. Se conserva este ADR exclusivamente como historial de decisiones y del límite de atomicidad de SAF.

## Objetivo
- Una identidad de biblioteca, no una biblioteca por dispositivo. Originales inmutables direccionados por SHA-256; mismo contenido = mismo original, no mismo título. El dispositivo conserva únicamente caché de libros descargados, datos locales para lectura offline y cola duradera de operaciones.
- Un estado lógico autoritativo con catálogo, metadatos, etiquetas, colecciones, relaciones, sinopsis, favoritos, notas, marcados, versiones, marcadores, posiciones y bajas. Un único archivo Biblioteca.json (o base transaccional equivalente) si el transporte permite actualización condicional real.
- Una copia portable única BibliotecaAI-copia.zip, independiente del estado activo, completa y verificada. Un solo escritor coordinado; las claves BYOK no salen de la instalación. No crear copias periódicas con nombres nuevos.
- En Drive: Libros/<sha256>.<formato>, Biblioteca.json, BibliotecaAI-copia.zip. Nombre de fichero visible no sustituye hash ni ID estable. Si biblioteca es grande, no reescribir todo un ZIP para una nota.

## Diagnóstico
Main 9019da52d04583167deb80aeb4a31b78079e978c: SharedLibrary admite almacén de árbol y ZIP por propietario, con inventarios distintos; compartir una carpeta visual no integra automáticamente ambos. Cada publicación de árbol tiene UUID y secuencia, cada instalación su JSON de posiciones y su ZIP de backup. La sincronización lógica deduplica catálogo por hash pero no garantiza unicidad física ante dos escrituras simultáneas o subida interrumpida antes de publicar recibo. El último estado válido por propietario se integra; no basta elegir el archivo más reciente de toda la carpeta.

## Restricción técnica que bloquea un archivo mutable multiwriter sobre SAF
Android DocumentsProvider concede permisos de archivo o árbol, no una transacción distribuida ni compare-and-swap de versión. Un mutex local, comprobar hash antes de escribir o leer después de escribir no garantiza exclusión entre dispositivos: A y B leen v1, ambos verifican v1, A escribe v2A y verifica, B escribe v2B y verifica; se pierde A aunque ambos informen éxito. El caso offline/caché agrava el problema. Un lock en archivo creado o escrito mediante SAF tampoco tiene creación condicional garantizada por todos los proveedores. No usar un JSON, ZIP o SQLite compartido escribible desde todos mediante SAF. No confundir Drive binario con edición colaborativa de Docs.

Fuentes oficiales: https://developer.android.com/guide/topics/providers/document-provider ; https://developer.android.com/reference/android/provider/DocumentsProvider ; https://developers.google.com/workspace/drive/api/guides/manage-revisions . La API Drive y SAF no son equivalentes; historial de revisiones no es bloqueo. El ADR-008 prohíbe actualmente API Drive/OAuth/cuentas externas.

## Opciones
A. Preservar solo SAF y sin servicios: una biblioteca lógica deduplicada, escritor por dispositivo con un diario propio y consolidación eventual; no prometer un único archivo físico mutable ni ausencia de duplicados transitorios. Un coordinador fijo puede generar un solo estado y backup, pero las operaciones de otros dispositivos requieren buzones duraderos o comunicación y no se confirman hasta que dicho coordinador esté disponible. No elegir un escritor por reloj, nombre ni lock file.
B. Coordinador transaccional (preferido si se autoriza un servicio): una biblioteca y un estado lógico, escrituras por operaciones idempotentes con revisión/transaction compare-and-swap, verificación de originales y publicación de backup desde único escritor. Puede materializar el JSON y ZIP en Drive si se autoriza acceso servidor a Drive; emparejamiento seguro de dispositivos, sin necesidad de usar las claves IA como credenciales. Evaluar identidad, permisos, costes, cuotas, almacenamiento y API concreta antes de implementar. No incluir secretos en APK/repositorio. Requiere decisión expresa sobre acceso al servicio y cambio de ADR-008 si corresponde. No crear despliegues ni activar Supabase/OAuth por defecto.

## Contrato transaccional requerido
- Cada operación: libraryId, deviceId, operationId único, revisión base, tipo, entidad estable, versión/hora. Cola persistida antes de mostrar cambios confirmados; servidor acepta idempotentemente y devuelve revisión confirmada. Si CAS falla, volver a leer y aplicar operaciones pendientes; no reemplazar snapshot completo. Conservación de lápidas y deduplicación de IDs de operación; resolver ediciones simultáneas de notas sin perder contenido (versiones o conflicto explícito); posiciones por último cambio efectivo, no máxima página; reloj sesgado tratado por protocolo de revisiones. No resucitar bajas salvo reimportación explícita posterior.
- Alta de libro: consultar hash, reservar clave única de biblioteca+hash de forma atómica, subir solo si no existe verificado, verificar tamaño y SHA-256; confirmar catálogo después. No borrar copia local hasta confirmar persistencia y, para importación central, copia ZIP completa. Si hay fallo, reintento desde cola. Mismo hash con títulos distintos no duplica original. Distintos hashes no se fusionan por título.
- Backup único: snapshot consistente de revisión confirmada, ZIP portable con todos los originales verificados, restauración ensayada y sustitución por único escritor; si fallo o backup parcial, no perder último completo. Frecuencia inicial conservar 12 h y altas centrales según PR #97, sin cambios silenciosos a política. Si posible destino físico independiente de Drive para proteger pérdida de cuenta.
- UI: Biblioteca completa / Dispositivo / Copia de seguridad (fecha, revisión, número de libros, integridad y pendientes). Los dos equipos deben mostrar la misma libraryId y última revisión; al desconectar se informa pendiente, sin falsos éxitos.

## Migración y validación
1. Inventario solo lectura de ambos tipos de almacén, copias y JSON. Capturar hashes, propietarios, revisiones, notas, lápidas, posiciones y discrepancias. No inferir integridad por fecha/tamaño. Crear backup independiente verificado; no borrar originales.
2. Construir catálogo destino en staging, fusionar por hash/IDs e historial; reconciliar versiones y bajas. Verificar número de libros, hashes, notas y posiciones; probar restauración. Conservación de claves IA y estado de descarga por dispositivo.
3. Cambiar todos los dispositivos de protocolo/identidad, detener escritores y workers antiguos antes del corte; los clientes incompatibles no publican en el nuevo estado. Revisar cola offline. Mantener carpeta anterior en solo lectura para rollback; no limpiar archivos históricos automáticamente.
4. Pruebas de dos/ tres dispositivos simultáneos: misma importación concurrente, cambios a notas distintas y a la misma nota, posiciones hacia delante y atrás, eliminar vs importar, cliente offline y retorno, duplicados, caída en publicación y backup, permisos revocados y reinicio. Verificar convergencia y no pérdida. CI emulado no demuestra Drive físico.
5. Solo tras verificar ambas instalaciones y recuperación, presentar plan de retirada de archivos antiguos; ningún borrado de datos reales en esta fase.
